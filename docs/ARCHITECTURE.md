# Как устроен агент вида Claude Code

Документ описывает архитектуру, а не конкретную реализацию. Claude Code закрыт,
поэтому здесь собраны принципы, которые видны из публичной документации, из
открытых аналогов (OpenCode, Claude Agent SDK) и из поведения любого агента с
инструментами. Ничего не декомпилировалось и не копировалось.

d3m3nk0 повторяет эту схему целиком, но в упрощённом виде.

---

## 1. Главная идея: модель — не агент

Языковая модель умеет только одно: получать сообщения и возвращать сообщение.
Агентом её делает **цикл** вокруг неё:

```
пользователь → [ модель → запрос инструмента → выполнение → результат ] → ответ
                        ↑________________ повтор ________________|
```

Claude Code, OpenCode, Cursor, d3m3nk0 — все они крутят один и тот же цикл.
Разница только в качестве инструментов, политике доступа и интерфейсе.

## 2. Семь слоёв

| Слой | Задача | В d3m3nk0 |
|---|---|---|
| **Протокол модели** | превратить историю в запрос конкретного API | `src/core/providers.js` |
| **Агентный цикл** | крутить turn → tool → turn | `src/core/agent.js` |
| **Инструменты** | дать модели действия в мире | `src/core/tools.js`, `src/core/mcp.js` |
| **Политика доступа** | решить, что можно без спроса | `needsApproval()` в `agent.js` |
| **Контекст** | уложиться в окно модели | `compactIfNeeded()` |
| **Состояние** | сохранить и продолжить сессию | `src/core/session.js` |
| **Интерфейс** | показать поток и спросить разрешение | `src/main/`, `src/renderer/` |

## 3. Протокол модели

История — это не «переписка», а **протокол**. Каждое сообщение состоит из блоков:

```js
{ role: 'assistant', blocks: [
    { type: 'text', text: 'Сейчас посмотрю файл.' },
    { type: 'tool_use', id: 'toolu_01', name: 'read_file', input: { path: 'a.js' } }
] }

{ role: 'user', blocks: [
    { type: 'tool_result', id: 'toolu_01', content: '1: const a = 1;' }
] }
```

Ключевой момент: **результат инструмента — это сообщение пользователя**. Модель
не «вызывает функцию» напрямую; она просит, а хост выполняет и возвращает
результат как входные данные. Отсюда и название: tool use, а не RPC.

Два провайдера отличаются только упаковкой:

- **Anthropic**: `tools: [{name, description, input_schema}]`, блоки `tool_use` /
  `tool_result` внутри `content`.
- **OpenAI-совместимый**: `tools: [{type:'function', function:{...}}]`,
  `assistant.tool_calls[]` и отдельная роль `tool` с `tool_call_id`.

Поэтому в d3m3nk0 есть канонический формат и два адаптера. Добавить третий
провайдер — это написать ещё один адаптер, не трогая цикл.

## 4. Агентный цикл

Один `send()` — это не один запрос к модели, а цикл до `MAX_STEPS`:

1. Собрать запрос: system + история + схемы инструментов.
2. Стримить ответ. Текст уходит в UI сразу.
3. Если в ответе есть `tool_use` — проверить политику, выполнить, добавить
   `tool_result`, вернуться к шагу 1.
4. Если инструментов нет — цикл закончен, это финальный ответ.

Два практических правила, без которых агент «ломается»:

- **Предел шагов.** Иначе модель может зациклиться на одном и том же вызове.
- **Пара «запрос → результат» неразрывна.** Если обрезать историю, нельзя
  оставить `tool_result` без его `tool_use` — API вернёт ошибку.

## 5. Инструменты

Есть два вида, и это важное архитектурное решение:

- **Встроенные** — те, что всегда под рукой: чтение, запись, правка, поиск,
  запуск команды. Они знают о рабочей папке и её границах.
- **Внешние через MCP** — протокол, по которому сервер сам объявляет свои
  инструменты. Агент не знает их заранее: он спрашивает `tools/list` и получает
  схемы. Именно так REA отдаёт свои 263 инструмента.

MCP — это то, что делает агента расширяемым. Вместо «добавим ещё один
инструмент в код» появляется «подключим ещё один сервер».

Описания инструментов — тоже промпт. Модель выбирает инструмент по описанию,
поэтому формулировка «когда использовать» важнее реализации.

## 6. Политика доступа

Агент с правом запускать команды — это удалённое выполнение кода по решению
модели. Поэтому между «модель попросила» и «мы выполнили» стоит гейт:

| Режим | Что без спроса |
|---|---|
| `ask` | только чтение |
| `allow-edits` | чтение и правки, команды с подтверждением |
| `yolo` | всё |

Плюс второй барьер — границы рабочей папки: инструменты отказываются выходить
за неё, пока доступ явно не разрешён.

В Claude Code эта идея выражена как набор разрешений на инструмент и режимов
подтверждения; в d3m3nk0 она сведена к трём режимам, но принцип тот же.

## 7. Контекст

Окно модели конечно, а история растёт. Три стратегии, которые применяют все:

1. **Урезать** — выбросить начало истории (дёшево, теряет детали).
2. **Сжимать** — пересказать старые ходы моделью (дороже, сохраняет смысл).
3. **Выносить** — держать факты в файлах/памяти и подгружать по необходимости.

d3m3nk0 делает первое: `compactIfNeeded()` считает примерный объём токенов и
убирает начало, не разрывая пары инструментов. Второе и третье — в планах.

## 8. Состояние

Сессия — append-only журнал JSONL: одна строка на сообщение. Это даёт
бесплатно: восстановление после падения, аудит действий, возможность
продолжить разговор и сравнить поведение.

Важно: журнал пишется **до** следующего шага цикла, а не в конце. Иначе при
падении теряется ровно то, что привело к падению.

## 9. Интерфейс

UI ничего не решает — он отображает события и возвращает решения:

```
main: agent.send()
        ├─ assistant_text  → печатать посимвольно
        ├─ tool_start      → карточка «выполняется»
        ├─ permission      → карточка «разрешить/отклонить» → ответ обратно
        ├─ tool_end        → карточка «готово/ошибка» + вывод
        └─ idle            → разблокировать ввод
```

Рендерер изолирован: `contextIsolation: true`, `nodeIntegration: false`, доступ
только через `preload.js`. Файловая система и процессы живут в главном процессе.

## 10. Чем d3m3nk0 отличается

Сознательные упрощения первой версии:

- нет субагентов и параллельных задач;
- нет сжатия контекста моделью;
- нет хуков, плагинов, кастомных команд;
- один диалог на окно, без вкладок;
- политика доступа — три режима, без гранулярных правил.

Что уже есть и работает: стриминг, два провайдера, 7 встроенных инструментов,
MCP, подтверждения, границы папки, сессии, CLI-режим.

## 11. Порядок чтения кода

1. `src/core/providers.js` — как история превращается в запрос.
2. `src/core/agent.js` — сам цикл.
3. `src/core/tools.js` — что агент умеет.
4. `src/core/mcp.js` — как подключаются внешние инструменты.
5. `src/main/main.js` + `src/renderer/app.js` — как это показывается.
